Load Third-Party Scripts Only After Consent

The DSGVO and the ePrivacy rules do not care what your banner says. They care about what the browser requested. A vendor script placed in index.html has already sent the IP address by the time the banner renders, and no amount of blocking logic afterwards undoes that request. The only reliable gate is not shipping the tag at all until consent exists.

The three vendors below are local stub files under public/vendor/. Nothing in this demo contacts a real third party, but the injection, the network request and the side effects are real.

The rules this pattern satisfies

  • No pre-ticked boxes. Every vendor starts denied, and the stored record starts empty.
  • Refusing is as easy as accepting. Withdraw sits beside Consent, same size, same page, no second dialog.
  • Granular per purpose. Analytics, support and session recording are three decisions, not one.
  • Withdrawal at any time. The record is removable and the page tells you what it cannot undo.
  • Evidence. The consent record carries what was granted; a production version adds a timestamp and the text version the user saw.
  • No dark patterns. The demo does not make refusal slower or uglier than acceptance.

What to copy into a real app

  • Keep the consent state in a signal in a root service, and let every embed read it. Never let a vendor snippet decide for itself.
  • Inject the tag from a service, not from a template. A template that renders a script tag is a template you have to audit forever.
  • Store the record server-side too if you need to prove it in an audit; browser storage is deletable by the person you would be proving it against.
  • A Content Security Policy is the backstop: if a vendor host is not in script-src, a mistake in this code cannot leak anything. See the strict CSP demo.
